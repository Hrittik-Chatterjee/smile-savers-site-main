# Naming conventions

Measured from the actual codebase, not aspirational. The goal stated for this
document: an AI agent or new developer should be able to predict where something
lives, and what a class or token means, from its name alone — without opening the
file. Every rule below is checked against what the repo actually does, and every
inconsistency found is listed rather than silently smoothed over.

## 1. Files

| Kind | Convention | Example | Compliance |
|---|---|---|---|
| Component (`src/components/`, `src/modules/**/components/`) | `PascalCase.astro` | `TestimonialsSlider.astro` | 46/47 — see exception below |
| Layout (`src/layouts/`, `src/modules/**/layouts/`) | `PascalCase` + `Layout.astro` suffix | `LocationPageLayout.astro` | 7/7 |
| Page (`src/pages/`) | lowercase, kebab-case, Astro's routing conventions for dynamic segments | `privacy.astro`, `[slug].astro` | 20/20 |
| Script (`design-intelligence/scripts/`) | lowercase, kebab-case, `.mjs` | `category-palette.mjs` | consistent |

**Exception found:** `src/modules/legal/legal.astro` — lowercase, and named after
its directory rather than its purpose. Investigated rather than assumed: **it is
dead code.** Nothing imports it, it isn't under `src/pages/` so Astro's router
never renders it, and it's the sole consumer of the `legal` content collection,
which has zero entries in `src/content/legal/`. The real `/privacy` and `/terms`
routes are separate, hardcoded pages that don't use this module at all. This one
file breaking convention is a symptom of being unintegrated, not a naming bug to
fix in isolation — flagged here rather than silently renamed or deleted, the same
way the earlier TinaCMS residue was flagged pending confirmation before being
removed (2026-08-21, once confirmed abandoned).

## 2. Component-scoped CSS class prefixes

Astro scopes `<style>` blocks per component automatically (via a `data-astro-cid-*`
attribute), so class names never collide across components at runtime. That
safety net is exactly why the *human-readable* prefix convention had been allowed
to drift — nothing broke, so nothing forced consistency. It drifted a lot:

| Component | Prefix used | Derivable from the name? |
|---|---|---|
| `TestimonialsSlider` | `tsl` | No — arbitrary consonant sample |
| `HomeCTA` | `hcta` | Partially |
| `TeamGrid` | `tg` | Only if you already know the scheme |
| `ContactForm` | `cf` | Only if you already know the scheme |
| `ContactInfo` | `ci` | Collides in spirit with `ContactForm`'s `cf` — inconsistent depth |
| `LocationMap` | `lm` | Only if you already know the scheme |
| `OfficeHours` | `oh` | Only if you already know the scheme |
| `PageHeader` | `ph` | Only if you already know the scheme |
| `BeforeAfter` | `ba` | Only if you already know the scheme |
| `ValuesList` | `vals` | Partially |
| `CTASection` | `ctas` | Yes |
| `ServiceCard` | `svc` | **No — inconsistent with its own siblings, see below** |
| `ServiceGrid` | `service` | — |
| `ServicesPreview` | `services` | — |

**The worst finding:** three components in the same domain use three different
prefix depths for the same word — `ServiceCard` → `svc-`, `ServiceGrid` →
`service-`, `ServicesPreview` → `services-`. An agent that has seen `service-`
used by `ServiceGrid` has no way to predict that `ServiceCard` uses `svc-`
instead. This is a real ambiguity, not merely an aesthetic one: editing "the
service prefix" without checking the actual file risks touching the wrong
component's styles in a merge or a broad find-replace.

**Note on the four `*PageLayout` components:** all four use the generic `page-`
stem internally, which is only safe *because* each is scoped to its own file by
Astro — reading `.page-header` in isolation cannot tell you which of the four
layouts it belongs to. This is the same class of risk as the Service* collision,
just lower-stakes because layouts change far less often than content components.

### Rule going forward

New components should NOT invent an arbitrary abbreviation. Derive the prefix
mechanically: **lowercase, first letter of each capitalised word, unless the
component is a single word, in which case use the whole word if ≤6 characters
or its first 4 letters if longer.** Examples: `TestimonialsSlider` → `ts` (not
`tsl`), `ServiceCard` → `sc` (not `svc`), `Hero` → `hero`. This is not applied
retroactively — renaming 47 files' worth of CSS classes and their markup
references is real regression risk for a cosmetic gain. It governs new work only,
and is checked by `npm run lint:design`'s existing pattern-matching approach
(a future rule, not yet implemented — see open items).

## 3. Design tokens

Four tiers, documented fully in [`colour.md`](./colour.md) for the colour system
specifically. The general scheme across all domains:

```
--{domain}-{role or scale-step}[-{state}]
```

| Domain prefix | Examples | Count |
|---|---|---|
| `color` | `--color-primary`, `--color-brand-surface`, `--color-interactive-primary-hover` | 77 |
| `cat` | `--cat-cyan-ink`, `--cat-cyan-tint` | 8 |
| `spacing` | `--spacing-scale-1..14` (numeric), `--spacing-section`/`-block`/`-element` (semantic, fluid) | 17 |
| `radius` | `--radius-sm..2xl`, `--radius-card`, `--radius-full` | 7 |
| `shadow` | `--shadow-sm..xl` | 4 |
| `font` | `--font-family-*`, `--font-size-*`, `--font-weight-*` | 17 |
| `duration` / `ease` / `transition` | motion tokens | 5 / 4 / 3 |
| `grid` / `container` / `breakpoint` | layout tokens | 10 / 6 / 5 |

**Self-inflicted inconsistency found and fixed this pass:** the spacing-scale
tokens added earlier in this session were named `--space-1..14`, a different stem
from the pre-existing `--spacing-section/-block/-element`. Two prefixes for one
domain is exactly the kind of drift this document exists to prevent — caught by
re-auditing my own work, not by an external report. Renamed to
`--spacing-scale-1..14` before it acquired any consumers (verified zero
`var(--space-*)` references existed in `src/` at the time of the rename).

## 4. Props and component contracts

Every `interface Props` field audited across all 47 components is camelCase, with
no exceptions found. This is the one naming dimension with zero drift — worth
recording as a positive baseline, not just cataloguing problems.

## 5. Content collections

Schema field names in `src/content.config.ts`: consistently camelCase, no
snake_case found. Collection names themselves (`services`, `team`, `testimonials`,
`legal`, `locations`, `glossary`, `comparisons`, `personas`) are plural nouns,
consistently.

## 6. Scripts and tools

`design-intelligence/scripts/*.mjs`: kebab-case, verb-or-noun-first
(`palette.mjs`, `category-palette.mjs`, `brand-tokens.mjs`, `design-lint.mjs`).
Consistent.
